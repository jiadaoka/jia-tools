# 需求文档

只做一件事：把谈拢的东西，写成一份**别人能照着开工**的文档。

`predev` 谈的是「够不够开工」，这里写的是「写下来之后还站不站得住」。两件事会分别失手：谈清了但写散了，接手的人照样得重问一遍；写得漂亮但边界破了，开发按错的基线做。

## 0. 先接住档位

提问预算继承 `predev` 的档位，不重新算：

| 档位 | 这里的做法 |
| --- | --- |
| 玩具 | 不写文档。五条地板写进 `PREDEV.md` 就够了 |
| 小工具 | 写下面的必需 5 节，其余按需 |
| 项目 | 全 8 节 |

档位没定过就先问一句，不要默认最大档。

**提问节奏**：每轮 1–3 个问题，每节确认一次再往下。不要一次一个磨到底（那是给不熟悉这块系统的人用的），也不要一轮甩十个（那是一轮里没想清楚）。每问都带建议答案，用户才有东西可以否。

## 1. 三条边界

写文档时只回答一个问题：**这条信息是给谁看的？**

| 写 ✅ | 不写 ❌ |
| --- | --- |
| 产品/用户看得见的行为、交互、限制 | 实现路径（"用 X 存""在 X 层算"） |
| 输入输出数据的业务含义 | 技术选型、框架、库、SDK |
| 与外部系统的对接边界（接什么、传什么） | 协议、通信方式、性能测试指标 |

判定口诀：**用户感知得到吗？** 感知得到就写，感知不到就不写。

用户混入实现细节时，剥出需求语义，然后一句话告知「这是实现细节，归设计阶段」。不要辩论，也不要照抄进文档。

**只出稿不出代码**：需要写业务 JS 才能演示，说明这一层越界了。要真的能跑，那是实现，不是文档。

## 2. 入口分流

| 场景 | 前置 | 做法 |
| --- | --- | --- |
| 0→1 新建 | 无需基线 | 基线填「无」，只写本次 |
| 在已有需求上迭代 | **必须**有上游基线：文档路径 + 版本号 | 先读基线，再写「基线 → 本次」的差异 |

基线拿不到就停下来要。**不允许在没有基线的情况下自由发挥**——写出来的"现状"十有八九是想象。

同模块/同业务域的历史文档只用来补上下文（术语、既有约束、可复用的结构），**不作基线**。两者混用，是迭代文档最常见的错。

## 3. 范围

- 用「**本次做什么 / 本次不做什么**」组织。不要用「v1 范围」这类说法——它会被读成"第一阶段做"，而 V1 就是本次。
- **不做项必须精简**：只列与本次最可能混淆、或最容易引发范围蔓延的项。穷举等于没划范围。
- **废弃项不进「不做」**：确认过"不再考虑"的东西，从全文删干净。留在不做项里，等于暗示"以后可能做"。
- **愿景性概念不进本期范围**：听起来宏大但本次不落地的词，标成"未来方向"，或直接删。

判定口诀：用户说「废弃/不做/不考虑/不要」时，先分清是**本期不做（V2 评估）**还是**已废弃（全文删除）**。这两者写错，后面所有范围讨论都会跑偏。

## 4. 结构

默认三层：**模块 → 功能 → 功能点**。颗粒度细时扩到四层（模块 → 子模块 → 功能 → 功能点）。

- 按业务能力切，不按页面或按钮切。「单按钮」不是模块，「按钮所在页面」才是。
- 用户明确给了模块架构，就按他的；没给就自己提炼，然后让他确认一次。
- 顶层（平台/大菜单）不进功能节，在背景里用一句话路径带过。
- **模块简述 ≤ 2 句**：第一句说做什么（动词开头），第二句说为什么。超过两句就是还没想清。

## 5. 每个功能点要写到的

| 项 | 要求 |
| --- | --- |
| 优先级 | P0（不做本期无法发布）／P1（不做核心价值受损）／P2（资源允许就做）／P3（留待以后）。**P0+P1 才是本期范围** |
| 强度 | 用 MUST / SHOULD / MAY / MUST NOT。全是 MUST 等于没分级 |
| 负面要求 | 涉及写、删、改的功能点，**必须**有一条 MUST NOT 说明什么绝对不能发生 |
| 多方案 | 有多个可选方案时**不要替用户选**，记成待决策项，写清选项、偏好、权衡维度 |

反面要求常被漏掉，而它恰恰是评审时最容易问到的：「那误删了怎么办」。

## 6. 字段与依赖

**字段**只列有数据交互的，纯 UI 文本（按钮文案）不进表。

- 字段名用业务术语：写「用户标识」不写 `user_id`，写「产生时间」不写 `timestamp`。
- 类型只到 `string / number / boolean / enum / object / array`，不写 `int32`、`varchar(255)`。
- 有默认值必须在说明列写明。这一条能省掉开发最常问的那句"不填怎么办"。
- 必填只填是/否。「条件必填」写进业务规则，不要塞进这一列。

**依赖**三分类，每行都要能回答"接什么、传什么"：

| 类型 | 判定 | 额外要求 |
| --- | --- | --- |
| 必须 | 没有它本功能不可用 | 缺失时宁可明确报错，不许假装成功 |
| 可选 | 没有它仍可用，体验下降 | **必须写明缺失时的行为** |
| 外部 | 不属本系统/本团队 | 按必须或可选处理，取决于业务约束 |

## 7. 验收与非功能

**验收点写可观测行为，不写实现指标。**

| 写 ✅ | 不写 ❌ |
| --- | --- |
| 「导出完成后文件在下载目录，含标题、链接、时间」 | 「导出成功率 ≥ 99%」 |
| 「对象不存在时提示'对象不存在'，而不是空白页」 | 「接口返回 404 时 toast」 |

四类验收，一个点只归一类：功能（按需求工作）／边界（边界条件下正确）／链路（跨模块协同）／回归（旧能力没被破坏）。至少覆盖两类。

**非功能**走五维：性能、容量、安全、可用性、兼容性。只写**对用户/产品有约束的项**（"回答上限 30 秒"），不写测试方法（"P99 < 2 秒"）。全都不适用就省略这一节，不写"无"。

## 8. 待确认事项

三分流，判定问句是「**业务方能拍板吗**」：

| 类别 | 判定 | 落处 |
| --- | --- | --- |
| 业务/产品体验层 | 业务方说得出是/否、30 秒/60 秒 | **进表**，标「建议需求最终确定」 |
| 灰色地带 | 看着像实现，但含产品体验边界（输入长度上限、大小写敏感） | **进表**，标确认方：需求定 还是 交设计确认 |
| 纯技术 | 后端接口、框架、技术选型、测试方法 | **不进表**，归设计/开发阶段 |

用户说「我不知道」时：追问一次；仍拒绝就按「需求方应负责」标 TBD，不要自己替他定。

## 9. 骨架

必需 5 节，按需 3 节：

```markdown
# <feature> — 需求

- 版本：v<major>.<minor>（首版 v1.0，每次变更小版本 +1）
- 状态：草稿 / 已发布未评审 / 已评审通过
- 日期 / 作者
- 上游基线：0→1 填「无」；迭代填「基于 <路径> v<版本>」

## 1 概述        <!-- 背景、产品形态（一句话路径）、角色、本次做什么/不做什么 -->
## 2 范围        <!-- 0→1：本期建设目标与关键约束；迭代：基线→本次的 新增/修改/删除 -->
## 3 功能模块    <!-- 模块简述 + 功能点（含优先级与 MUST NOT）+ 页面需求 + 本模块依赖 -->
## 4 验收清单    <!-- 模块 / 验收点 / 类型 / 验证方法 -->
## 5 待确认事项  <!-- 模块 / 待确认内容 / 建议确认方 / 建议处理方式 -->

## 6 字段属性    <!-- 按需：对象 / 字段 / 类型 / 必填 / 约束 / 说明 / 数据来源 -->
## 7 非功能      <!-- 按需：性能 / 容量 / 安全 / 可用性 / 兼容性 -->
## 8 修订记录    <!-- 按需：最新在顶，每次变更 +0.1，标版本状态 -->
```

页面需求可为空（纯逻辑模块留空，不要写"无"）。这一节只写入口在哪、点击后怎么流转、有哪几个状态；**颜色、字号、间距不写**，那是设计稿的事。

## 10. 自审

写完自己过一遍，两类：

**跨节一致**：概述里的模块名 = 功能模块 = 验收清单 = 待确认事项；字段属性里的对象 = 功能点涉及的对象。

**边界干净**：全文搜实现词（存储、框架、协议、组件库名）应为 0 命中；搜愿景词应为 0 命中；搜"以后再说"这类模糊表述应为 0 命中。

发现问题直接改，然后把整份文档给用户看。

## 11. 交付

只问三件事：**哪里写错了？哪条其实是假设？缺了什么？**

改完存进项目约定的位置（有仓库规范就按规范命名，没有就用 `docs/<feature>.md`），并告诉用户：这份文档可以直接交给设计或开发，也可以接着用 `predev-req-ui` 翻成页面。

之后决定变了，**先改文档再改代码**，并在修订记录加一行。文档写完就可以不动，除非决定变了。
