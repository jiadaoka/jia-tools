# 需求 → 界面

先翻页，再画。

跳过翻译直接开画，出来的是一堆好看的页面，不是**这个需求**的页面。前端拿到之后第一句话一定是「这里为什么有两个入口」。

## 0. 先分清交给谁

| 这份 HTML 会不会离开这个会话 | 用什么 |
| --- | --- |
| 不会，只是我自己看「对不对」 | `predev-sketch`：一次性、不抛光、不进主干 |
| 会，前端要照着它写 | 本技能：产物要能独立读，还得站得住 |

判据只有这一条。判错的代价不对称：把一次性原型做重，浪费几小时；把交付稿做轻，前端重画一遍。

## 1. 开工两问

只问两个，问完就动手：

1. **几个独立场景？**（一个独立页面、一个独立状态、一种独立形态各算一个）
2. **有没有现成的产物？**（现有样式文件、现有页面截图、现有设计稿链接，任意一项即可）

有现成产物就走迭代（§8），没有就走全量。用户说「大概三四个」就先按四算，画出来再删，比反复确认快。

档位继承 `predev` 的判定：玩具不画交付稿。

## 2. 先翻页

按顺序翻，翻完再动笔。五张表，都不长：

**① 页面类型**——从业务特征落到页面类型：

| 业务特征 | 页面类型 |
| --- | --- |
| 搜索、筛选、批量处理、导出、看记录 | 列表页 |
| 看单条记录、分组信息、关联记录、操作日志 | 详情页 |
| 新建、编辑、提交、校验、草稿 | 表单页 |
| 审批、多角色处理、步骤推进、填意见 | 审批页 |
| 指标、趋势、总览、下钻 | 看板页 |
| 配规则、开关、阈值、映射 | 配置页 |

**② 拆页**——一个需求里出现这些组合就默认拆开：

| 需求信号 | 拆成 |
| --- | --- |
| 查询 + 看详情 | 列表页 + 详情页 |
| 列表 + 新建/编辑 | 列表页 + 表单页（或抽屉表单） |
| 列表 + 批量操作 | 列表页 + 批量操作弹窗 |
| 配置 + 风险动作 | 配置页 + 二次确认弹窗 |

「做一个客户管理页」不是需求，是三个页面的缩写。拆不清就先拆，别混成一句。

**③ 功能点 → 页面模块**——每个功能点都要在页面上有落位：

搜索 → 查询区 + 搜索/重置；多条件筛选 → 查询区 + 可折叠高级筛选；批量操作 → 表格上方操作栏；导出 → 页头或工具栏动作；看详情 → 操作列 + 详情跳转；删除 → 危险动作 + 二次确认；上传 → 表单区上传模块 + 上传中/失败态。

**④ 字段 → 交互**：名称/编号 → 单行文本；状态/类型/级别 → 枚举选择；起止时间 → 日期范围；金额/数量 → 数字 + 单位；负责人/部门 → 人/组织选择；备注 → 多行；布尔规则 → 开关；层级分类 → 级联；附件 → 上传。

**⑤ 状态矩阵**——每页默认补全，除非需求明确说不需要：

| 状态 | 必须回答 |
| --- | --- |
| 默认态 | 第一次进来看到什么 |
| 加载态 | 数据没回来时怎么表现 |
| 空状态 | 没结果时给什么文案和动作 |
| 错误态 | 查询/保存失败怎么提示 |
| 成功态 | toast、跳转，还是局部刷新 |
| 禁用态 | 哪些字段/按钮不可操作 |
| 无权限 | 哪些角色只能看不能改 |
| 处理中 | 导出/提交进行中怎么锁动作 |

**权限也要翻**：「仅管理员可编辑」→ 普通用户隐藏或置灰并说明原因；「已结束记录不可修改」→ 表单只读、危险动作隐藏；「部分字段仅某人可见」→ 表单和详情都标可见性。

**动作必须有结果**：搜索→刷新列表；重置→清空并回默认结果；保存→留在本页并给反馈；提交→跳详情或回列表；删除→确认后回列表；导出→按钮 loading，完成或失败给反馈。只写动作名不写结果，等于没设计。

## 3. 翻不清的先记下来

翻的过程中必然有模糊点。**不许脑补**，单列成一张表带进产物：

| 模糊点 | 要标注什么 |
| --- | --- |
| 页面数量 | 单页、多页，还是页 + 弹层 |
| 字段来源 | 用户输入、系统生成，还是接口来 |
| 权限 | 谁可见、谁可改、谁可操作 |
| 动作结果 | 成功后跳转、刷新，还是停留 |
| 状态 | 是否需要 loading/empty/error/无权限 |

模糊点写清楚了，画的时候才有边界；藏着不写，画出来的每一屏都在替用户做决定。

## 4. 画之前先定方向

五格填完再动手，每格一两行：

- **主题**：这是什么产品、给谁、主要工作是什么。写不出来就先回去问。
- **色**：4–6 个命名值，每个写作用（底、面、主文字、次文字、强调、状态）。**优先沿用项目已有的一套**，没有才现定。
- **字体**：一到两族，写清角色。能用一族就一族。
- **布局**：一句话 + 一个 ASCII 框，标出内容怎么对齐。
- **独特**：一句「什么让它只可能是这个产品」。

交付稿和一次性原型的区别在这里：一次性原型可以只填个大概，交付稿要**执行到底**——定了克制就处处克制，定了高密度就处处高密度。

落地时守三条：颜色/字号/间距/圆角只从上面定的那套取，页面里不现编一次性值；样式集中在 `styles.css`，HTML 里不写 inline style；类名有意义，前端能照着猜结构。

## 5. 产物

```
<项目>/design-<日期>/
  index.html          # 卡片式导航，列出全部 screen，可点击进入
  styles.css          # 唯一一份样式，所有 screen 共用
  screens/
    01-<场景名>.html  # 一屏一文件
    02-<场景名>.html
```

硬要求：

- **一场景一文件**。不要把所有场景堆进一个文件，前端没法拆。
- **序号全局连续**（01、02、03…），不按分组重编号，不在标题里加 `§`。
- 每屏顶部有可点的返回 `<a href="../index.html">← 返回总览</a>`。
- 用真实的中文名、真实的数字、真实的文案。**不许 Lorem ipsum、不许 `xxx`/`___` 占位**。

## 6. 设计稿和演示稿不许混

两种产物，两拨受众，混在一起两边都不能用：

| 产物 | 给谁 | 只放什么 |
| --- | --- | --- |
| 设计稿 `screens/` | 前端 | 页面本身：结构、状态、真实内容 |
| 演示稿 | 评审会 | 页面 + 导航 + 注解 + 高亮 |

设计稿里**不要**出现导航栏、注解气泡、高亮浮标、折叠按钮、评审备注、"注："这类东西。想指给人看，另做一份演示稿，别污染设计稿。

## 7. 每屏硬要求

- 主体是一个完整高保真实例，其他状态以**变体**形式接在下方，只换核心区域，页面框架不动。
- **每屏至少 1 个非默认状态**，整套至少 2 个异常边界（网络失败、权限不足、对象不存在、数据为空任选）。
- 每个按钮有 hover/active/disabled 反馈，不允许"看着能点但没反应"。
- 每页标出从哪来、能回哪去。
- 文字不许折行叠字：按钮 `white-space: nowrap`，容器宽度不够就允许横向滚动，不要挤到换行。
- 子元素不超出父容器。

## 8. 迭代：复用 > 重生成

用户给了任何一项现成产物（现有 `styles.css`、现有页面截图、现有设计稿链接、现有交接文档），就走迭代，**不重出设计系统**。

- 基于现有文件改，不要另起一套。
- 只做受影响的页面，其余原样保留。
- 只标变更元素：新增/修改的给一个标记，旧元素不带。
- 变更说明单独一份，写清改了哪个页面的什么，以及前端怎么还原成干净页面（删标记块、删样式块）。
- 用户已经说清改了什么的，直接做，不要反复确认；只有真正模糊时才问一句。

反例：迭代时把七个场景全量重画一遍；把旧元素的标记也重新打一遍；每改一版就重新问一遍范围。

## 9. 现状要可溯源

需求涉及"改已有功能"时，界面必须建立在**看过的东西**上，不是想象上。三层，上层够用就不进下层：

1. **索引**：先看现有页面清单/菜单，定位在哪个入口下。
2. **已有资料**：现有的设计稿、截图、组件说明、旧页面 HTML。
3. **实测**：上面的都对不上，才去打开真实页面看。

三条红线：

- 没看过就不许写"现在这里是这样"。
- 资料会过期，和实测冲突以实测为准，并注明差异。
- 查看过程**只读**：不删、不清空、不提交。不确定的交互先问。

## 10. 收手

问题被回答了就停。

- 结论回 `PREDEV.md` 或需求文档：改一条决定，或补一条假设。
- 产物留在 `design-<日期>/`，交给前端就是它的终点；不要顺手把它变成项目工程。
- 画的过程中发现「这需求该有几个页面」本身就没定，说明问题不在界面，在需求——回去补 `predev-req`，比继续画更有价值。

**不要让设计稿变成项目。** 它一开始需要"重构"，你已经在写正式实现了——那就正式立项，或者扔掉重来。
