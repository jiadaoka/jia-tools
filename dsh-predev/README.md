# dsh-predev

> 开发之前：把想法问到够开工，写成 `PREDEV.md`；要交出去时写成需求文档，要交前端时翻成设计稿。需要看效果时做非真原型。

## 安装

在 `jia-tools` 根目录执行：

```sh
dsh plugin --profile desktop add .\dsh-predev
```

重启 profile 后生效。卸载：

```sh
dsh plugin --profile desktop remove dsh-predev
```

## 技能

### predev

讨论，然后约定。先问「这东西你打算投多少」，按投入档位给提问预算（玩具 ≤5 问，小工具 ≤15 问，项目不设上限），然后按轮推进：一轮把整个前沿问完，停下等回答。

每个问题都带推荐答案——用「建议」而不是「你看呢」，你才有东西可以否。查事实是它的活，决定才是你的。停下来时把五条地板补满：一句话、收手线、怎么跑起来、第一个切片、不做什么，然后写进项目根的 `PREDEV.md`。

那里只有两种句子：已定的决定（一句能被反驳的话）和待验证假设（写清怎么验证）。把假设混进决定里是最常见的自欺。

### predev-req

把谈拢的东西写成一份别人能照着开工的需求文档。提问预算继承 `predev` 的档位——玩具不写文档，小工具写必需 5 节，项目写全 8 节；节奏改成每轮 1–3 问、每节确认一次，而不是一次一个磨到底。

三条边界定生死：只写产品可见行为、数据的业务含义、对外对接边界；实现路径、技术选型、协议一律不进。判定口诀是「用户感知得到吗」。另有三条最容易写错的：不做项必须精简、废弃项要从全文删掉（留在"不做"里等于暗示以后会做）、愿景词不进本期范围。

自审两类：跨节模块名对齐，全文实现词 0 命中。

### predev-sketch

非真原型，回答一个「得看看才知道」的问题。先分清是哪种问题：界面该长什么样、状态对不对、数据形状够不够、流程顺不顺——四种问题四种介质，画板、单文件 HTML、一张表、箭头图。

选中介质的标准只有一条：能让你最快看见「不对」的那个，不是最像成品的那个。「非真」是硬约束：一眼假、单文件、内存态、不抛光、只做被问的那一件事、不进主干。界面档要先填五个格子（主题、4–6 个命名色值、字体角色、布局一句话、一句「什么让它只可能是这个产品」）再动手。

问题被回答了就停，结论回 `PREDEV.md`。

### predev-req-ui

`predev-sketch` 的反面：这一份要离开会话，前端照着它写。分工判据只有一条——**这份 HTML 会不会离开这个会话**。判错代价不对称：一次性原型做重了浪费几小时，交付稿做轻了前端重画一遍。

先翻页再画：页面类型 → 拆页 → 功能点落位 → 字段到交互 → 八态状态矩阵 → 权限翻译 → 动作必须有结果。翻不清的不许脑补，单列成待确认。产物是一屏一文件 + 一份 `styles.css` + 一个总览页，序号全局连续；设计稿里不许出现导航、注解、浮标高亮——那是演示稿的事。

### predev-wait

一句话技能。上一条没听懂时用：要求先给背景、用短句、一句话只说一件事、专业名词先解释或者别用，且不要复述整段历史。模型不会自动调用它，只认你手打。

## 它防的是什么

同一个人会轮流掉进两个坑：

- **过度松懈**：直接开写，写到一半发现方向没想清，推倒重来。
- **过度设计**：动第一行代码之前就想把设计想完美，想两周，一行没写，然后没兴趣了。

第二个坑更常见。所以第一原则不是「想清楚一切」，是**够开工**。这两种结果的差别，决定了问多少问题、在哪停。

第三个坑在写下来之后：**以为说过了就等于写下来了**。对话会被压缩、会被下次会话遗忘，文件不会。而写下来的东西只要边界破了（写了实现、范围没砍、现状靠想象），接手的人还得把整件事重问一遍——所以需求文档那两条技能盯的不是"写全"，是"写住"。

## 一次访谈

第一步永远先问投入档位。不问就往下问，是这类技能最常见的死法：一个周末玩具被问三十个问题，问到你想放弃为止。

| 档位 | 判据 | 预算 |
| --- | --- | --- |
| 玩具 | 只有你用，坏了不心疼 | ≤ 5 问，1 轮 |
| 小工具 | 你会长期用，或几个人用 | ≤ 15 问，2–3 轮 |
| 项目 | 别人会用，要维护一年以上 | 不设上限 |

假设是玩具，一轮把整个**前沿**问完：

```
❓ Q1 - 收手线：导出到什么程度算做完？
➡️ 建议：一个收藏夹产出 .md，含标题、UP 主、链接、收藏时间。不做分页。

❓ Q2 - 怎么跑起来：命令行还是网页？
➡️ 建议：单文件脚本。你自己用，不需要网页。

❓ Q3 - 数据从哪来：官方 API 还是抓页面？
➡️ 建议：我去查，不占用你的决定。

❓ Q4 - 不做：这次明确不做什么？
➡️ 建议：不做登录态管理、不做图片下载、不做批量。
```

三件事值得注意：

- **Q3 不是问题。** 查事实永远是插件的活，只有**决定**才排进队列。
- 一轮问完就停。你的回答会解锁下一轮。
- **五条地板齐了就停**，哪怕前沿还没空。剩下的推迟到写代码时再定。

过筛只有一条标准，**改主意的代价**：几分钟就取默认值不问，几天就进队列，要重写就排最前面。

## 非真原型

「非真」是硬约束。原型的目的不是能用，是**能看出对不对**。它一眼就该看出是一次性的：单文件、内存态、不接真数据、不抽组件、不进主干。

先分清在回答哪个问题，再选介质：

| 问题 | 介质 |
| --- | --- |
| 界面该长什么样 | 画板（draw2code）或线框 |
| 状态／逻辑对不对 | 单文件 HTML，按钮驱动，状态全打印 |
| 数据形状够不够 | 一张表，或一段写死的 JSON |
| 流程顺不顺 | 画板上的箭头，每步一句话 |

界面档不直接画。先填五个格子——主题、4–6 个命名色值、一到两族字体、布局一句话、一句「什么让它只可能是这个产品」——再画，画完换掉全部文案自查一遍。视觉选择来自题材本身，不是来自好看的模板；只在一处用力，其余安静规整。

## 结构

```
dsh-predev/
  index.js              # 插件本体：读 skills/*/SKILL.md，注册进 ctx.skills
  cordis.patch.yml      # bundle 补丁层，按包名引用插件
  package.json          # dsh.bundle manifest
  skills/
    predev/SKILL.md         # 档位、过筛、前沿、五条地板、停止线、PREDEV.md 结构
    predev-req/SKILL.md     # 三条边界、入口分流、范围、结构、字段/依赖、验收、待确认、自审
    predev-sketch/SKILL.md  # 四档介质、六条硬规则、界面方向
    predev-req-ui/SKILL.md  # 翻页五表、八态矩阵、产物契约、设计稿与演示稿分区、迭代复用
    predev-wait/SKILL.md
  scripts/check.mjs     # 自检
```

没有 `templates/`、没有 `references/`：技能正文自足，模板就是 `predev` 里那段结构、`predev-req` 里那个骨架，界面检查表就在 `predev-sketch` 和 `predev-req-ui` 里。多一个文件就多一条会断的路径。

改技能就是改 `skills/` 下的 Markdown，重启生效。改完跑自检：

```sh
node scripts/check.mjs
```

它用桩 `ctx.skills` 跑一遍 `apply()`，检查五个技能都在、名字和目录一致、调用策略正确、frontmatter 合法、技能之间的引用没有断，以及正文里没有漏进具体产品或某家设计系统的名字（条款一旦绑死在某项目上，换项目就整段作废）。

## 来源

追问问法与「一次性原型」原则改编自 [mattpocock/skills](https://github.com/mattpocock/skills)（MIT）的 `grilling`、`prototype`、`wait-what`；界面方向方法来自 `frontend-design` 技能（Apache-2.0）。两处都做过重写，不是原文搬运。

`predev-req` 与 `predev-req-ui` 的条款改写自团队内部的需求工程技能包（需求分析 + 原型生成那一套），只取了换项目仍成立的部分：边界、范围、结构、验收、待确认、页面翻译、状态矩阵、产物契约。设计系统事实（组件库、色板、布局骨架、设计 token）、具体产品的仓库与命名规范、已废弃的多轮评审机制，全部留在原处没有搬——那些换一家公司就不成立。
