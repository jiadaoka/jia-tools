# 怎么判

一条意见的价值取决于它是否**可被证伪**：能指出哪一行、什么条件下、造成什么后果。缺任一条，它就不是发现，是猜测。

## 1 只在变更行上说话

评论必须指向本次 diff 新增或修改的行。行号以 `head` 提交为准，`路径:行` 或 `路径:起-止`。

同一问题涉及多处时最多列 3 处，其余写「等 N 处」。写完报告抽查 2–3 条行号，对不上就重取——错的行号比没有行号更伤信任。

## 2 现状写事实，不写判断

**现状**只描述当前代码在做什么，≤3 句。需要佐证时紧跟着贴 fenced code block，只贴关键 5–15 行，用 `// ←` 标出问题行。

标题写现象，不写结论：

| 可以 | 不行 |
|---|---|
| 批量保存按实例提交，跨实例无事务 | 建议优化事务 |
| 循环内按主键逐条查库（N+1） | 性能需要提升 |
| 空集合返回 `null`，调用方直接 `.size()` | 建议处理空值 |

## 3 影响必须落到后果

写「谁、在什么条件下、遇到什么」。可以落到：数据错、用户可见、越权、崩溃、性能数字、维护成本。

不写「可能有问题」「建议关注」「存在风险」——这类词把「不知道」伪装成「知道」。

**说不清触发条件就不报。** 判不准是不是真问题就丢弃；判不准该报多重就取低一级（`high` 与 `medium` 之间取 `medium`）。

## 4 四类最常见的假阳性

- **只在极端输入下才成立**，而那个输入被上游校验挡住——去读调用方，别只看被调方。
- **代码看起来重复，其实是两件会分头演化的事**——重复的判据是「改一处必须同时改另一处」，不是「长得像」。
- **「没有错误处理」**，但这一层的契约就是抛出，由外层统一兜——先看有没有统一兜底。
- **「建议加注释 / 建议改名」**，而它不影响任何人做判断——这类归 `low`，且全篇不超过 3 条。

## 5 分类只选一个

`bug` / `security` / `performance` / `maintainability` / `test` / `style` / `documentation` / `other`。

分类影响读者的处理顺序，不是给问题贴标签：一个「少了空值判断导致 NPE」是 `bug`，不是 `maintainability`。

## 6 建议给最小改法

写能直接动手的 2–3 条，不重写整个方法。确实需要重构时，写清分几步、每步之后代码还可用。

「建议重构」「建议统一风格」不是建议，是没想清楚。

## 自检

1. 这条能指到具体一行吗？
2. 触发条件写得出来吗？写不出来就该丢。
3. 影响是后果还是形容词？
4. 我读过它的调用方吗？
