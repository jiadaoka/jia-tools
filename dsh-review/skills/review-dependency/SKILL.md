# 审依赖改动

写代码时「要不要引入」的判断不在本文。本文只管改动已经存在之后，审的人能看到、而作者容易漏掉的那几件。

依赖的成本不在加的那一行，在之后每个人都要承担的那份不确定：它还会不会维护、带进来什么、下一个人遇到问题查不查得到。

## 1 锁文件要与声明一致

一次「加一个包」顺带升级了 40 个包，是这类改动最高频的问题——没人审得了，也没人知道为什么。

核对方式：锁文件 diff 里新增、移除、改版本的包名，逐条对应 `package.json` / `go.mod` / `Cargo.toml` 的改动。对不上的列出来，不合并成一句「锁文件有变动」。

## 2 判实际装成的版本，不判范围

清单里写 `^1.2.0`，锁文件里可能是 `1.2.3`，也可能被提升到 `1.9`。漏洞、行为差异、可用 API 都按实际装的那个判。

要读的事实：锁文件里的解析结果、依赖树里这个包的实际版本。

## 3 漏洞分两种，处理相反

- **有修复版本**：报 `security`，建议升到修复版本。
- **无修复版本**：报 `security`，同时给出缓解措施或替代方案。只写「有漏洞」等于把问题丢回给作者。

判的是实际版本上是否存在该漏洞，不是清单里声明的范围。

## 4 同一个能力不该有两套

两套 HTTP 客户端、两套日期库、两套表单校验、两套状态管理——之后每个人都要猜「新的该用哪套」。

判据不是「两个包功能重叠」，是「会不会有人不知道该用哪个」。会，就是 `maintainability`，且比「写法不好看」重一档：它持续产生分歧。

例外：为替换旧包而并存的过渡期。这种要写清旧包什么时候删、还剩哪些调用方。

## 5 审的人能看到、作者看不到的两处

- **传递依赖**：作者看直接依赖，审要看依赖树里被带进来的东西——体积、许可证、已知漏洞。
- **删除时的残留**：删依赖要看还有没有调用方。声明删了、代码里还在 import，到构建时才炸。

## 自检

1. 锁文件里每一处变动都能对应到声明改动吗？
2. 版本判的是范围还是实际装成的那个？
3. 漏洞写了「有没有修复版本」吗？
4. 这个包会不会和现有某个包是同一件事？
5. 删依赖时，确认没有调用方残留了吗？
