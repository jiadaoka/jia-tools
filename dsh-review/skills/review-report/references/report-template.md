# 审查报告模板

这份文件是报告格式的唯一规范。照抄骨架，按 `review-report` 的判据填。

## 一、章节骨架

```
# {主题} — {审查对象} 审查报告 R{轮次}

> 裁定：{✅ 可继续 | ⚠️ 修完再看 | ❌ 停 | 🚫 信息不足}
> 统计：🔴 critical {n} · 🟠 high {n} · 🟡 medium {n} · 🟢 low {n} · 🔵 info {n}

## 1 元数据
## 2 覆盖清单
## 3 问题清单
### 3.1 🔴 critical（{n}）
### 3.2 🟠 high（{n}）
### 3.3 🟡 medium（{n}）
### 3.4 🟢 low（{n}）
### 3.5 🔵 info（{n}）
## 4 规则核对
## 5 结论
```

问题按严重度分组，组内按 diff 顺序排。五个分组标题恒存在，空组写「无。」。

## 二、元数据（§1）

固定 8 行，一行不缺；同一行多个值用 ` / ` 分隔。

| 字段 | 示例 |
|---|---|
| 审查对象 | `jia-tools` 工作区改动 |
| 仓库与路径 | `E:\project\engineering\jia-tools` |
| 范围 | 工作区未提交改动（含 3 个未跟踪文件） |
| 提交 | head `4fb5fa4` / merge-base `439783f` / 1 commit |
| 变更规模 | 19 文件，+544 / -69（可审 10） |
| 审查时间 | 2026-11-09 17:20 (Asia/Shanghai) |
| 轮次 | R2（前序报告见同目录，结论不复述） |
| 审查工具 | Open Code Review v1.13.3 + dsh-review |

范围写清楚是哪一种：`base..head` / 单提交 / 工作区未提交改动。文件数写「变更总数（可审数）」，让读者知道有多少被排除规则挡掉了。

## 三、覆盖清单（§2）

行数与 `files.txt` 严格相等。

| # | 文件 | 变更 | 结论 |
|---|---|---|---|
| 1 | `src/kernel.js` | M +66/-14 | ⚠️ H-1 M-2 |
| 2 | `src/report.js` | A +180 | ✅ |
| 3 | `package-lock.json` | M +1200 | — 未审：锁文件 |

结论列只有三种：`✅` / `⚠️ {编号}` / `— 未审：{原因}`。

表下一行写总账：

```
覆盖 3/3 个可审文件；未审 1 个（锁文件，工具判定为不可审）。
```

「未审」与「不可审」要分开说：被 `review_scope` 排除的不算未审。

## 四、问题清单（§3）

```
#### H-1 保存前未校验同名目录，重复节点同时入库

- **定位**：`src/directory/service.js:118-124`
- **类别**：bug
- **现状**：插入前只查了同层节点数量，未按 `(parentId, name)` 查重；并发请求下两次插入都能通过。
- **影响**：同一目录下出现两个同名节点，前端树按名字建 key，渲染出重复行且无法删除其一。
- **建议**：唯一约束下沉到库（`uk_dir_parent_name`），服务层捕获唯一键冲突转成业务错误。
```

要贴代码时放在**现状**之后：

````
```js
// ← 只查数量，没有查重
if (countByParent(parentId) > 0) { ... }
```
````

各组门槛：

| 分组 | 贴代码 | 条数 |
|---|---|---|
| critical | 必须 | 不限 |
| high | 必须 | 不限 |
| medium | 能贴则贴 | 不限 |
| low | 不贴 | ≤3 |
| info | 不贴 | ≤3 |

## 五、规则核对（§4）

只核对与本次变更文件类型相关的规则条目，不整本抄。

| 规则条目 | 结论 | 依据 |
|---|---|---|
| 循环内不查库 | ⚠️ M-2 | 第 3 行按主键逐条查 |
| 空集合返回空集合 | ✅ | 全程 `emptyList()` |
| SQL 只出现在数据层 | ✅ | 服务层无字符串拼接 |
| 表结构变更需迁移脚本 | — | 本次无 schema 变更 |

结论只允许 `✅` / `⚠️ {编号}` / `—`。

没有加载到规则（`review_rules` 不可用）时，本节写「本次无规则基线，问题均按通用工程原则判」——不假装有规则。

## 六、结论（§5）

```
## 5 结论

**裁定：⚠️ 修完再看**

{3–5 句。只讲当前代码的状态与本次改动的影响，不复述历史轮次，不写修复历史。}

待修：
1. 🟠 H-1（保存前按 (parentId, name) 查重）
2. 🟠 H-2（删除节点未级联清理关联表）

可以晚点改：🟡 M-1、M-2

仅提示：🔵 I-1
```

裁定口径见 `review-report` §4。`info` 不进待修清单。

## 七、写作禁令

- 不写「前轮问题修复验证」。
- 不写「已验证无问题的设计」清单——覆盖表的结论列已经表达。
- 不复述 diff、不贴整段新增代码。
- 不报 diff 之外的存量问题。
- 不写纯提问式模糊项。
- 单份报告 80–200 行；超过 300 行说明在复述代码。
