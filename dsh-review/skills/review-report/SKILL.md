# 怎么落

格式不是排版偏好：它决定了报告能不能被快速扫读、结论能不能被追溯。**章节不增、不减、不换序；空章节照写并标注「无。」**

完整骨架与逐节要求见 `references/report-template.md`，这里只说不可偏离的部分。

## 1 五档，前四档才是缺陷

| 色标 | 等级 | 判据 |
|---|---|---|
| 🔴 | `critical` | 本次改动会直接造成数据损坏、越权、凭据泄露或不可用；必须写清触发条件 |
| 🟠 | `high` | 可导致安全漏洞、数据丢失、崩溃或核心功能失效 |
| 🟡 | `medium` | 性能问题、错误处理缺口、边界条件、可维护性缺陷 |
| 🟢 | `low` | 风格、可读性、非关键最佳实践；全篇 ≤3 条 |
| 🔵 | `info` | 不构成缺陷但值得记录；全篇 ≤3 条，每条写明「为什么不算缺陷」 |

`info` 不是第五档缺陷：不计入缺陷数、不参与裁定、不进入结论的待修清单。**把该报的问题塞进 `info` 降级，等同漏报。**

色标是冗余提示，不替代等级词：标题写 `🔴 critical（2）`，不写 `🔴（2）`。

## 2 每条问题五个字段

```
#### {编号} {一句话标题}

- **定位**：`{路径}:{行号}`
- **类别**：{bug | security | performance | maintainability | test | style | documentation | other}
- **现状**：{当前代码的事实，≤3 句}
- **影响**：{谁在什么条件下遇到什么后果，≤2 句}
- **建议**：{可执行改法，≤3 条}
```

编号 = 等级首字母 + 组内序号（`C-1` / `H-1` / `M-1` / `L-1` / `I-1`）。编号只是引用标识，等级由所在分组决定，不跨组共用序号。

不使用 `P0/P1`、`严重/一般/轻微`、`阻断/建议` 等另一套等级词。

## 3 覆盖清单必须对账

清单来自 `review_scope` 落盘的 `files.txt`，**逐行对应、条数相等**。

结论列只允许三种写法：`✅` / `⚠️ {编号}` / `— 未审：{具体原因}`。

- 未审必须给原因（生成物、纯改名、二进制、读不到），不许留空。
- 一行一个文件。要合并同构文件时，在审法上合并、在清单里仍逐份列出。
- 审完自己数一遍：覆盖表行数 == `files.txt` 行数。不等就是没审完，不许写「覆盖 N/N」。

## 4 结论只按裁定表

| 条件 | 裁定 |
|---|---|
| 存在未解决的 `critical` | ❌ 停 |
| 最高为 `high` | ⚠️ 修完再看 |
| 仅 `medium` / `low` | ✅ 可继续 |
| 仅 `info`（或无任何条目） | ✅ 可继续 |
| 范围不完整、head 不明、关键文件读不到 | 🚫 信息不足 |

`info` 永远不参与裁定，只在结论末尾单列一段「仅提示：🔵 I-1」。

偏离上表必须在裁定后紧跟一句「偏离理由：…」。顶部状态行的裁定必须与 §5 一致。

## 5 写作禁令

- 不写「前轮问题修复验证」章节。旧问题仍在就按当前代码重报，用本轮新编号。
- 不复述 diff、不贴整段新增代码、不解释修改意图。
- 不报 diff 之外的存量问题。
- 不写纯提问式的模糊项（「是否应该…」「建议确认…」）——判不了就降级或转 🚫。
- 不用形容词替代结论：「基本通过」「应该没问题」不出现。
- 80–200 行是常态。超过 300 行说明在复述代码。

## 6 落位与命名

```
<repo>/.review/<单元>/
  meta.md        审查对象、范围、提交、轮次、是否含未提交文件
  files.txt      review_scope 落的范围清单
  report.md      当前轮报告；多轮时改为 <单元>_R<n>_<yyyyMMddHHmm>.md
```

单元名由 `review_scope` 给出（`LOCAL-<仓库名>-<时间戳>`）。多轮审查沿用同一单元，轮次累加，不换目录。

`.review/` 应该进 `.gitignore`——它是审查产物，不是代码。第一次落盘时提一句，让用户自己决定要不要提交其中某份报告。

## 自检

1. 五个分组标题都在吗？空的写了「无。」吗？
2. 覆盖表行数等于 `files.txt` 行数吗？
3. 每条的五个字段齐吗？影响是后果还是形容词？
4. 结论和顶部裁定一致吗？
5. 有没有哪条问题其实指向 diff 之外的行？
