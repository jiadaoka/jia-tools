# 审什么

**范围不是我想的，是工具给的。** 调 `review_scope`，它返回 `reviewable_files`、`excluded_files`（含原因）、`mode` 与取 diff 的命令。那份清单就是契约：报告里的覆盖表必须与它逐行对应。

## 1 每次审全量，不审增量

`base..head` 之间的**全部**变更都要读，包括前几轮改过的文件、上一轮的修复补丁、上一轮新增的文件。

**不继承上一轮结论。**「上轮已通过」「上轮已修复」都不是跳过理由。修复补丁引入新问题是高频来源，与普通新代码同等对待。

## 2 存量代码不审

`base` 之前就存在、本次未改动的代码不审、不报。这和「上轮审过的代码」不是一回事——上轮审过的仍在 diff 里，本轮必须重审。

存量代码如果确实是本次改动的前提风险，写进结论的一句附注，不占问题编号。

## 3 不越界

只审提供的仓库及其指定范围。未提供的仓库不检索、不推断、不报问题。

跨仓依赖按「假定已存在且正确」处理：前端调了一个新接口，只有后端也在范围内才核对契约；只给前端时，接口一律视为存在，不写「接口可能不存在」。

## 4 范围拿到的三件事要落到手上

| 拿到 | 怎么用 |
|---|---|
| `reviewable_files` + 落盘的 `files.txt` | 覆盖表的唯一来源。清单有几行，覆盖表就有几行 |
| `mode` + `merge_base` / `commit` | 决定取 diff 的命令形状，不要自己拼 ref |
| `excluded_files` 与原因 | 报告里豁免的文件要有出处。`unsupported_ext` 这类是工具判的，不是漏了 |

**未提交文件要单独确认。** `workspace` 模式的 `git diff HEAD` 看不到未跟踪文件；`review_scope` 会报它们为 `added`，取 diff 时整文件读——整份都是新代码。

## 5 同构文件捆成一组

多份 `messages*.properties`、双方言 SQL、多模块同款代码，合成一个审查单元，组内逐份核对。避免「审了一份、默认另几份一样」。

覆盖表里仍要逐份列出——分组是审法，不是省略的理由。

## 6 中断按进度续跑

超过 15 个文件时，把「已审 / 待审」写进 `<repo>/.review/<单元>/progress.md`，中断后从断点接着跑。不从头重来，也不凭记忆宣称审过。

## 自检

1. 覆盖表的行数和 `files.txt` 相等吗？
2. diff 里的每个文件都读过、或写明了不审的理由吗？
3. 有没有跳过一个文件，理由是「上轮看过」？
4. 报的问题都落在本次变更的行上吗？
