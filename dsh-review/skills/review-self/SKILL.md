# 审自己写的代码

自己审自己，失效方向与审别人相反：审别人容易看不出问题，审自己容易看不出**自己的盲区**——「我为什么这么写」的理由留在脑子里，代码里不一定有。

判据不因为作者是自己而放宽。同一条规则，写的时候按它执行，审的时候按它判。

对象包括两样：自己写的代码，和自己下的结论——「这个改动没问题」「这个方案可行」都要按同一套判据过一遍。

## 1 以代码为准，不以意图为准

「我知道这里要处理空值」不等于「这里处理了空值」。「这个分支走不到」不等于「它真的走不到」。

审查时只认代码里读得到的东西。意图要么写进注释或提交说明，要么不算数。

## 2 先审最没把握的地方

写的时候就记下哪几处不确定：某个 API 的签名、某个分支是否可达、某个库的默认值、并发下的顺序、某个字段是不是必填。

审查从这几处开始，不从文件头开始。全篇平摊注意力，40 行没问题的代码会掩盖那 3 行。

一处都想不起「没把握」，通常不是写得好，是假设还没被检验过——先去确认最基础的调用链，再谈审查。

## 3 三种自我背书

| 说法 | 它实际是什么 | 要换成什么 |
|---|---|---|
| 「已经实现了」 | 我写了代码，没确认它被调用到 | 哪个入口、哪条路径会走到 |
| 「跑过一次，通过」 | 一个用例通过 | 跑的哪条命令、覆盖了什么、没覆盖什么 |
| 「这里必须这样」 | 我有一个理由 | 理由是什么，不这样会出什么问题 |

三条里任何一条拿不出右列，结论里写「未证明」，不写「完成」。

## 4 未证明要写出来

交付时分两栏：

- **核对过的**：读了哪份代码、对了哪个契约、和哪个调用方逐行对上了。
- **没被证明的**：没跑过、没查到调用方、依赖的外部服务拿不到、只看了这一层没看上游。

「应该没问题」不算证明。这句话要么删掉，要么替换成它掩盖的那个事实。

## 5 自审读不出自己的假设

自审的产出是「我确认了什么、我怀疑什么」，不是「它是对的」。我没意识到的假设，我也审不出来——所以要把这个盲区说出来，而不是用一个「没问题」盖住。

需要「它到底行不行」的结论时，说清还缺哪一步验证，把验证交给能拿到真实输出的人。

## 自检

1. 我有没有因为「这是我写的」而跳过某一处？
2. 我最没把握的地方，排在第几条？
3. 结论里有几个「通过」是真正跑过并给出数字的？
4. 有没有一个「应该没问题」没被替换掉？
