# 权限点的粒度

权限表一旦按接口数量生长，就再也收不回来——最后没人配得清，于是所有人都有权限。

## 1 一个业务对象一个权限点

- **不按接口数量裂变**。增删改查是同一个对象的四种操作，共用一个点；裂变成四个点，最终没人配得清。
- **例外**：同一对象上存在完全不同的操作者角色时（比如普通用户只能看自己的，管理员能看全部），按角色分层，而不是按接口分层。
- **新权限点必须登记**：归属哪个对象、分配给哪些角色、默认值是什么。不登记等于不存在。

## 2 新增带权限的操作，先答四问

1. 这个操作需要服务端校验吗？（几乎总是需要，除非是完全公开的数据）
2. 需要展示级控制吗？（是否需要按角色隐藏入口）
3. 能否复用已有权限点？（优先复用，避免权限表膨胀）
4. 谁登记、挂在哪、分配给谁？

四问答不出来，就不要先写 `if (hasPermission(...))`——那是把设计问题推迟成了代码问题。

## 3 权限还没定稿时的中间态

现实里常常是「代码要交付，权限点还没批下来」。这时：

| 必须做 | 禁止做 |
| --- | --- |
| 留显式锚点（`TODO:` + 单号），写明终态 | 删掉判断——删判断不是修复，是把「看不见」换成「谁都能点」 |
| 登记待办，指定收尾人 | 拿另一类标识顶替（用请求级标识做展示级），它会恒假，入口对全员消失 |
| 写明中间态是「能看见、点下去报错」，并告知这是已知缺陷 | 静默上线，让使用方以为权限已生效 |

中间态不是终态。交付时必须说清当前是哪一种，不能让接收方自己猜。

## 4 自检

1. 权限点粒度是一个业务对象一个，还是按接口裂变了？
2. 新权限点登记了吗：归属、角色、默认值？
3. 中间态是否写了锚点、登记了待办、说清了终态？
