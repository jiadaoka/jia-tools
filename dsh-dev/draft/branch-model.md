# 分支模型

前缀名（`feature/`、`hotfix/`、`release/`、`dev`、`main`）可按团队实际命名替换，但**结构关系不变**。

## 1 铁律

> **只在开发分支上改代码。** 其余分支（主干、开发线、发布分支、支持分支）一律只读。

理由很简单：基线分支上的任何一次直接改动，都会让「这个版本包含什么」失去唯一答案。回滚、排查、发布说明全部依赖这个答案。

## 2 分支关系

```
main（主干，永远可发布）
  └── dev（开发线，集成分支）
        ├── feature/<单号>-<短描述>   从 dev 或最新 release 拉
        └── hotfix/<单号>-<短描述>    从 release 或 main 拉

release/<版本>   发布分支，创建即冻结
support/<版本>   历史版本支持分支
```

| 分支 | 允许改代码 | 来源 | 合并去向 |
| --- | --- | --- | --- |
| `feature/*` | 是 | `dev` 或最新 `release` | `dev` |
| `hotfix/*` | 是 | `release` 或 `main` | 双合：`main` + `dev` |
| `release/*` | 否 | `dev` | 冻结，只接受合并进来的修复 |
| `dev` | 否 | — | 只接受合并请求 |
| `main` | 否 | — | 只接受合并请求 |

## 3 关键规则

- **feature 从最新基线拉**：从过期分支拉出来的改动，合并时会带进一堆无关变更，评审无法聚焦。
- **release 创建即冻结**：冻结之后只在 release 上做「必须现在做」的修复，其余一律回 dev 排队。
- **双合不可省**：release 与 hotfix 的修复必须同时合回主干与开发线。只合一处，下次发版就会把已修的缺陷重新带回来——这类回归最难排查，因为「明明修过」。
- **回并冲突禁止强推**：解决冲突用正常的合并提交或重新应用；强推会覆盖别人已推送的提交。
- **合入走合并请求**：即使只有一个人改。理由不是流程洁癖，而是合并请求是审查与决策的留痕点。
- **分支名带单号**：`feature/<单号>-<短描述>`。半年后要回答「这个改动为什么存在」，这是最便宜的线索。

## 4 自检

1. 当前分支是什么？是允许改代码的分支吗？
2. 这个分支是从最新基线拉的吗？
3. 合并去向正确吗？修复类改动是否两边都合了？
4. 分支名带单号了吗？
