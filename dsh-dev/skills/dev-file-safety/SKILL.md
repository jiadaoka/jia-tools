# 改文件安全

目标只有一个：**不覆盖用户的手工改动，不制造无关 diff。**

## 1 动之前

- **完整读取**目标文件，不用片段推断整体。文件读不全（被截断、编码异常、体积过大），就停手并说明，不基于半个文件改。
- 识别「看起来是人工改过」的痕迹：格式与周围不一致、有手写注释、有临时调试残留、缩进风格突变、有被注释掉的块。这些地方要格外小心，改动前先说明你打算怎么处理。
- 确认改动范围：要改哪几处、每处的上下文是什么。范围说不清就先问，不要「先改改看」。
- **看工作区是否干净**。本来就有未提交改动时，先说一句「这些不是我改的」再动手——否则出问题无法归因。

## 2 怎么改

| 场景 | 做法 |
|---|---|
| 改既有文件 | **精确替换**：只替换目标片段，保留其余一切（空行、缩进、换行符、文件末尾换行） |
| 新建文件 | 整文件写入 |
| 大段重写 | 先说明为什么不能局部改，得到确认再动 |
| 批量同类修改 | 先做一处给人看，确认口径后再批处理 |

- 不整文件重写既有文件——即使内容「看起来一样」，也会丢格式、丢注释、丢不可见字符，产生一整片 diff。
- 不顺手格式化：改 A 功能时把整个文件缩进改一遍，会让真正的改动淹没在噪声里。
- 不改变换行符与编码。仓库用 LF 就写 LF；不确定就保持原样。
- 不删除你认为「没用」的代码。你觉得没用，可能是有原因的——注释掉的兼容、看起来多余的判空、没人调用的导出。

## 3 改之后

- **自查 diff**：确认只改了该改的地方，没有碰到无关位置，没有整体换格式，没有意外删除。
- 检查是否有调试残留（打印、临时开关、被注释的旧实现）。
- 如果 diff 比预期大，停下来找原因，不要用「反正改对了」放过。

## 4 改结构要同步断言

改数据结构、接口签名、序列化格式时，**在同一次改动里**更新结构断言与测试。

只改实现不改断言，测试会静默通过——它校验的还是旧结构，等于没有测试。新增分支补用例，删除分支删用例，不留永远不执行的死测试。

## 5 边界模糊时

「重构一下」「优化一下」「整理一下」这类指令，范围是模糊的。**先给具体选项对齐，再动手**：

```
可以按三种范围做，请选一个：
1. 只改 A 处（最小改动，风险最低）
2. 改 A + B（顺带修掉同一段的重复逻辑）
3. 整段重写（可读性最好，但 diff 大、需要回归验证）
```

范围模糊时直接动手，最常见的结局是改了一大片，然后被要求回滚——这时候连「哪些是用户的改动」都分不清了。

## 6 自检

1. 文件完整读过了吗？读不全时是否停手了？
2. 有没有识别出人工改动痕迹？处理方式说清了吗？
3. 是精确替换，还是整文件重写？为什么？
4. diff 里有没有无关变更、格式变化、意外删除？
5. 换行符与编码保持原样了吗？
6. 工作区原有的未提交改动，我动到了吗？
