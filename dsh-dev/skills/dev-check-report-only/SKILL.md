# 检查轮只出报告

用户说「看一下这个抽屉为什么关不掉」，他要的是**原因**。把 `v-if` 改成 `v-show` 再回一句「已修复」，他拿到的是一个不知有没有副作用的 diff，还得自己反推原来错在哪。

## 1 这一轮的交付物是报告

每条四项，缺一项就不是发现：

- **位置**：文件与行号，或页面、功能点、接口。
- **现状**：实际是什么样，贴关键代码或实际表现。
- **依据**：违反了哪条规范、哪份依据；规范没覆盖就直说这是判断项。
- **建议**：怎么改、改动范围多大。

级别可以标阻断 / 建议，但**改不改留给用户定**。

## 2 为什么不能边查边改

- **报告的价值是改动前的现场。** 交付时问题已经不存在了，用户既无法判断改得对不对，也无法否决哪几条不该改。
- **修复会改掉判断依据。** 改完再看，永远看不出原来错在哪，复查变成自证。
- **「顺手」通常越过范围。** 用户问 A 文件，报告里夹着 B 文件的改动，评审时两件事混成一件。

## 3 修复是另一个任务

确认要改之后**另开一轮**，按报告逐项修，修完重新验证；报告里把对应项标「已修」，**保留原问题描述与依据**，不整段覆盖成「已修」了事。

## 4 「检查并修复」的例外

两个动作都在授权内，顺序仍然不变：**先列问题，再动手**。报告里保留「修前 → 修后」对照，当前状态一栏写清哪几条已经改掉。

## 5 与审查包的分工

装了按范围出报告的审查包时，五档严重度、覆盖清单、报告骨架按它来。这条只管动作边界：**这一轮动不动手**——不重复它的格式要求。

## 6 自检

1. 用户要的是结论还是改动？我这一轮交的是哪一个？
2. 报告里每条都能指出位置、现状、依据吗？
3. 我是不是已经改了代码，然后才把结论补在报告里？
4. 报告的范围和用户问的是同一个范围吗？
