# 范围按点名，不按目录

需求文档常几份堆在一个文件夹里。于是有一个很容易滑过去的推断：**「文件夹里有」等于「本轮要做」。** 它不成立。

本轮做哪些，只由这次被点名的那几份决定。其余的不是「暂缓」，是**本轮不存在**。

## 1 三种越界

| 越界 | 长什么样 |
|---|---|
| 改代码 | 顺手替另一份需求修了它要的字段、加个判断、补个入口 |
| 改文档 | 把另一份需求的文档、原型一并「对齐」了 |
| 混实现 | 把另一份需求的字段、枚举、流程混进当前实现——尤其两份改了同一个字段时 |

还有第四种，最轻也最常见：**汇报里替它提改进建议**。看起来只是多说一句，实际把范围从「做了什么」扩到了「顺便评估了什么」，用户还得先判断这条建议该不该接。

## 2 撞车时以本轮为准

两份需求落在同一字段、同一接口、同一菜单上是常态。处理只有一条：**按本轮需求做**。

绕不开（比如同一张表的字段被两边要求不同含义）就一句话上报，由用户定。不自己跨需求调和——调和的结果一定是两边都不完全符合，而且没人知道自己被折中过。

## 3 不预读

只有本轮明确引用了某份公共接口文档、原型或附件，才去读，且**只取与本轮相关的那部分**。

顺手扫目录读出来的东西不会停在上下文里当背景：它会参与判断。读到另一份需求也改了 `alarmLevel`，接下来很自然就会「统一」它——不是纪律松了，是注意力被牵走了。

## 4 与依据只读同源

`dev-basis-readonly` 管「不为了让实现看起来对而改依据」，这条管「不因为目录里有就把它算进本轮」。两条合起来只服务一件事：**改动范围可界定**。范围说不清，用户就没法判断哪几处是这次该动的。

## 5 自检

1. 这次被点名的需求，具体是哪几份？说得出名字吗？
2. 我改的文件、动的字段，能对应到被点名的那几份里吗？
3. 有没有读到、改到、或在汇报里评价了本轮没点名的需求？
4. 撞了同一字段时，我是按本轮做的，还是自己折中了两边？
