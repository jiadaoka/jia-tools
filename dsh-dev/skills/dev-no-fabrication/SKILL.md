# 不臆造

核心一句话：**不知道就说不确定，不要用看起来合理的猜测把它填满。**

最危险的失败不是写错，而是**写得很顺、很像**——路径、字段名、配置项、库方法都合理，只是不存在。人读的时候不会怀疑，跑起来才发现，中间可能已经过了几轮评审。

## 1 不编

- 不编接口路径、字段名、配置项、环境变量、第三方库用法、命令行参数。
- **字段类型以契约为准**，不按字段名推断：`...Count` 未必是整数，`...Time` 未必是时间对象，`...List` 未必是数组。
- 不确定就停下来问。问之前先查（需求文档、接口定义、依赖源码、官方文档）——**先查后问，但不要用猜代替问**。
- 引用的库能力必须能指出出处：依赖里的哪个版本、哪个模块、哪个导出符号。给不出出处就不要用。

## 2 版本与能力现读

- 版本、可用 API、行为差异，**读实际安装的东西**：依赖清单、锁文件、包目录里的元数据、编译产物。
- 不凭文档快照、不凭记忆、不凭「上一个项目是这样」。
- 「我记得这个库支持」是最常见的错误来源。同一个库的大版本之间行为会变，同一个方法在不同平台上的语义会变。

## 3 自检

1. 我写的路径、字段、配置项、库方法，每一处都能指出出处吗？
2. 版本与可用能力，是读出来的还是想出来的？
3. 有没有哪个字段类型是我按名字猜的？
