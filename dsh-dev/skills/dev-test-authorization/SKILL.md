# 测试代码要单独授权

测试是**独立交付物**，不是业务改动的赠品。它和业务代码一样进评审、一样要维护、一样会烂——所以一样要跟着授权走。

## 1 什么算测试代码

单测、组件测试、E2E 脚本、快照、fixture 与 mock 数据，以及**为让用例跑起来而改的测试配置**。

最后一项最容易被漏掉：配置文件进本次 diff 之后，评审者看不出它跟这次改动有什么关系，而它影响的是下一次所有人的跑法。

## 2 四条边界

| 场景 | 做法 |
|---|---|
| 用户点名要测试 | 写，且只写他点的那一处，不顺带把周边组件、工具函数一并铺满 |
| 结构改动让旧断言失效 | 同一次改动里修完（见 `dev-file-safety` §4），修的时候不「补两条更稳的」 |
| 想覆盖但没授权 | 汇报里一句话：哪个点、什么风险。等决定，不先写好再补一句「顺手加的」 |
| 跑已有测试 | 是验证动作，不构成写用例的授权 |

## 3 越界的代价

业务仓库里的用例常常**没有维护人、没进流水线**。加进去既不防回归，又要跟着组件一起改；更麻烦的是它把「改一个字段」的授权范围悄悄扩成了「连测试基建一起动」，出了问题归因不到一处。

## 4 不写测试不等于不验证

验证按 `dev-verify-on-request` 给证据：读 diff、跑构建、实际操作界面，逐项标 ✅ / ❌ / ⏭️。**不为了凑一个 ✅ 去搭测试框架**——那是把没授权的事做成了交付物。

## 5 自检

1. 这一轮，用户点名要测试了吗？点的是哪一处？
2. 我新建的用例、fixture、配置，对应哪一句授权？
3. 旧断言失效了没修就说「测试通过」，还是修完了？
4. 想覆盖某个风险时，我是提了一句建议，还是已经写好了？
