# 依赖

每引入一个依赖，就多一个会变、会弃坑、会带漏洞的东西。所以门槛应该比自己写代码高一点。

## 1 引入前先查

现有依赖与标准库能不能解决同类问题？优先复用，不为「统一」另起一套。

## 2 新依赖要说清三件事

- 解决什么问题。
- 为什么现有方案不行。
- 体积、许可、维护状态是否可接受。

说不清第三条的依赖，通常是一个可以被砍掉的依赖。

## 3 漏洞

有已知高危漏洞且无修复版本时，**上报**。不静默升级、不静默忽略——两种做法都会把问题推给下一个人。

## 4 不为绕过构建问题

不降级依赖、不加 `--force`、不改锁文件、不注入环境变量来让构建通过。

绕过的代价是延迟的：本次绿了，下一个人拿到一个谁也不知道为什么这样的锁文件。构建问题先定位原因，再决定修法；真要临时绕过，写清原因、范围和拆除条件。

## 5 自检

1. 现有依赖里有现成方案吗？
2. 为什么要新增，说不说得清？
3. 有没有用 `--force` 或降级换来的绿？
4. 锁文件动了吗，为什么动？
