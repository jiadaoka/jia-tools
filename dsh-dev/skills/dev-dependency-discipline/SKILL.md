# 依赖

每引入一个依赖，就多一个会变、会弃坑、会带漏洞的东西。所以门槛应该比自己写代码高一点。

## 1 引入前先查

现有依赖与标准库能不能解决同类问题？优先复用，不为「统一」另起一套。

## 2 新依赖要说清三件事

- 解决什么问题。
- 为什么现有方案不行。
- 体积、许可、维护状态是否可接受。

说不清第三条的依赖，通常是一个可以被砍掉的依赖。

## 3 漏洞

有已知高危漏洞且无修复版本时，**上报**。不静默升级、不静默忽略——两种做法都会把问题推给下一个人。

## 4 构建失败先归因，再决定修法

构建与安装由开发者发起（见 `dev-verify-on-request`）；这一节处理的是**他把失败输出贴回来之后**的归因顺序。别急着改配置：

| 先查 | 怎么查 | 为什么它排在前面 |
|---|---|---|
| 运行时版本 | 项目要求的 Node / JDK / Python 版本，对照本机 | 版本不对时，所有报错都是它的下游症状 |
| 端口与进程 | 上一次的 dev server / 监听进程是否还占着 | 「构建卡住」「端口被占」几乎是残留进程 |
| 依赖装没装 | 依赖目录是否存在、锁文件是否与清单一致 | 换机器、切分支后最常见的一类 |
| 既有失败 | 这个错误在我改动之前是否已存在 | 不区分就会把存量问题当成自己引入的，改错地方 |
| 网络与镜像 | 私有源、代理、证书 | 只影响拉包，不影响编译 |

排完仍不确定时：**记录现象 + 问**，不要靠改配置试出来。判断「是不是环境问题」这件事本身需要证据，不需要猜。

## 5 不为绕过构建问题

不降级依赖、不加 `--force`、不改锁文件、不注入环境变量、不改 `scripts` 来让构建通过。

绕过的代价是延迟的：本次绿了，下一个人拿到一个谁也不知道为什么这样的锁文件或构建脚本。真要临时绕过，写清原因、范围和拆除条件，并留下可搜到的标记。

## 6 自检

1. 现有依赖里有现成方案吗？
2. 为什么要新增，说不说得清？
3. 有没有用 `--force` 或降级换来的绿？
4. 锁文件动了吗，为什么动？
5. 构建失败时，我先排了版本、端口、依赖、既有失败这四项吗？
