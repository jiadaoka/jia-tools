# 规范优先

**已有代码 ≠ 规范。** 仓库里存量代码多，只说明历史长，不说明它合规；新增和修改的代码一律以**书面规范**为准。

这条决定所有其他条款是否生效：如果「存量即规范」，那么任何条款都只是建议。

## 1 两种来源，别混

「跟随现有代码」说的是**来源**问题，不是**效力**问题：

- **来源**：几个模块写法各异时，写法只能参考真实存在的代码——不凭空发明，不拿「更好的写法」替换存量，不跨模块强行统一。
- **效力**：规范覆盖的场景，依据是规范，不是代码。

混在一起就会得出「存量优先于规范」的错误结论——那不是原意，是对原意的误读。

## 2 决策顺序

1. **先查规范**：这次改动涉及哪些场景？有没有对应条款？
2. **再读相邻代码**，只取三样：业务上下文、可复用的 helper 是否已存在、这是历史遗留还是项目惯例。
3. **冲突时以规范为准**：新代码按规范写；存量违规不复制、不扩散。
4. **规范没覆盖** → 跟随目标文件现有写法，并标 `TODO:` 说明缺口。
5. **拿不准** → 停下来问，不边猜边写。

## 3 新增与修改的差别

| 场景 | 要求 |
|---|---|
| 新增文件、组件、接口、查询、配置 | 按规范，不参照存量违规写法 |
| 修改既有代码（规范已覆盖） | 改到哪按哪的规范写，不扩大到无关代码 |
| 修改既有代码（规范未覆盖） | 保持该文件现有风格，不引入第二种模式 |
| 纯改名、移动、格式化 | 不动逻辑，不触发规范检查 |
| 紧急修复 | 先解决问题，事后补对齐并标 `TODO:` |

## 4 差异分两类，处理相反

| 类型 | 判断标准 | 处理 |
|---|---|---|
| **契约差异** | 下游依赖它，改了要动调用方 | 跟目标模块 |
| **违规差异** | 规范明确禁止，或缺了规范要求的东西 | 不跟，新代码按规范写 |

一句话：**这个差异是「别人依赖它」还是「规范禁止它」？前者跟，后者不跟。**

不「现代化」：不因为新版本有更好的写法就替换存量模式，除非本次任务就是重构。

## 5 反模式

| 反模式 | 正确做法 |
|---|---|
| 「相邻文件这么写，我跟着写」 | 先查规范 |
| 「仓库里已经有这种写法，所以合规」 | 数量多 ≠ 合规 |
| 「规范没说，就照抄相邻文件」 | 按 §2 落笔 + 标 `TODO:` |
| 借这次改动顺手重排整个文件 | 只改本次触达的范围 |

## 6 自检

1. 这次改动涉及的场景，规范查过了吗？查的是哪一条？
2. 我参照的相邻代码，是合规写法还是历史遗留？
3. 我跟随的差异，是契约还是违规？
4. 有没有顺手改了与任务无关的存量代码？
