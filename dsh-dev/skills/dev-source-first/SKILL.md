# 规范优先（元规则）

## 1 一句话

**已有代码 ≠ 规范。** 仓库里存量代码多，只说明历史长，不说明它合规；新增和修改的代码一律以**书面规范**为准。

这条听起来简单，但它决定所有其他条款是否生效：如果「存量即规范」，那么任何条款都只是建议。

## 2 两种来源，别混为一谈

「跟随现有代码」这句话，说的是**来源**问题，不是**效力**问题：

- **来源**：几个服务/模块写法各异时，写法只能参考真实存在的代码——不能凭空发明、不能拿「更好的写法」替换存量、也不能跨服务强行统一。
- **效力**：规范覆盖的场景，依据是规范，不是代码。

把这两件事混在一起，就会得出「存量优先于规范」的错误结论——那不是原意，那是对原意的误读。

## 3 决策顺序（每次改动前走一遍）

1. **先查规范**：这次改动涉及哪些场景？项目里的规范文件有没有对应条款？
2. **再读相邻代码**，但只取三样东西：
   - 业务上下文（这个模块在干什么）
   - 可复用的工具/helper 是否已存在
   - 判断这是「历史遗留」还是「项目惯例」
3. **冲突时以规范为准**：新代码按规范写；存量违规不复制、不扩散。
4. **规范没覆盖** → 跟随目标文件/目标模块现有写法，并标 `TODO:` 反馈规范缺失。
5. **拿不准** → 停下来问，不边猜边写。

## 4 新增与修改的差别

| 场景 | 要求 |
|---|---|
| 新增文件 / 组件 / 接口 / 查询 / 配置 | **MUST** 按规范，不参照存量违规写法 |
| 修改既有代码（规范已覆盖部分） | 改到哪按哪的规范写；同一处顺手矫正可以，**不扩大到无关代码** |
| 修改既有代码（规范未覆盖部分） | 保持该文件现有风格，不引入第二种模式 |
| 纯改名 / 移动文件 / 格式化 | 不动逻辑，不触发规范检查 |
| 紧急修复 | 先解决问题，事后补对齐并标 `TODO:` |

## 5 规范未覆盖时怎么落笔

- 以**目标文件所在模块**的现有写法为参考。不同模块的返回结构、命名、异常风格本来就不同，**不要跨模块强行统一**。
- 不「现代化」：不因为新版本有更好的写法就替换存量模式，除非本次任务就是重构。
- 不发明：接口路径、字段名、配置项、第三方库用法都必须有出处（需求 / 接口文档 / 官方文档）。
- 写完后标 `TODO:` 说明「规范未覆盖，跟随 X 模块现有写法」，让下一个人知道这是有意的，不是疏忽。

### 5.1 差异分两类，处理相反

| 类型 | 判断标准 | 处理 |
|---|---|---|
| **契约差异** | 下游调用方依赖它，改了要动调用方 | **跟目标模块** |
| **违规差异** | 规范明确禁止，或缺了规范要求的东西 | **不跟**，新代码按规范写；存量不顺手批量改 |

一句话判据：**这个差异是「别人依赖它」还是「规范禁止它」？前者跟，后者不跟。**

例子（跨语言通用）：

- 契约：模块 A 的接口统一返回包装对象，模块 B 直接返回数据对象——跟所在模块，别统一。
- 违规：某个接口漏了统一鉴权注解、某个类名与本项目分层约定不符——不跟，新代码按规范写。

## 6 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 「相邻文件这么写，我跟着写」 | 相邻文件可能本身就是违规存量 | 先查规范再决定 |
| 「仓库里已经有这种写法，所以合规」 | 数量多 ≠ 合规 | 查规范 |
| 「为了和同模块一致，用旧写法」 | 一致性是 SHOULD，规范是 MUST | 新代码按规范 |
| 「规范没说，就照抄相邻文件」 | 相邻代码只是参考，不是依据 | 按 §5 落笔 + `TODO:` |
| 「目标模块本来就是这么写的」 | 没区分契约与违规，欠账被当成惯例继承 | 按 §5.1 判 |
| 借这次改动顺手把整个文件重排 | 改动面失控，审查无法聚焦 | 只改本次触达的范围 |

## 7 自检

1. 这次改动涉及的场景，规范查过了吗？查的是哪一条？
2. 我参照的相邻代码，是合规写法还是历史遗留？能说清吗？
3. 规范没覆盖的地方，我是不是跨模块抄了另一种风格？
4. 我跟随的「现有写法」，是契约还是违规？
5. 有没有顺手改了与任务无关的存量代码？
6. 该标 `TODO:` 的地方标了吗？
