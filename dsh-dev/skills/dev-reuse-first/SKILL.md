# 先复用，再新建

**判据不是「用哪个库」，是「这个需求属于哪一类」。**

| 这一类 | 先搜什么 | 要沿用的东西 |
|---|---|---|
| 接口调用 | 已有的同服务 / 同端点的调用 | 参数形态、响应解构、错误处理、loading 与重试 |
| 组件 | 组件库里有没有、共享层有没有同类 | 命名、props、组合方式 |
| 工具函数 | 共享 utils 里有没有同能力 | 入参出参、边界处理 |
| 界面文案 | 已有的文案常量或语言文件 | 同一句话不要有两份写法 |

找不到就扩到同模块的相邻文件；还是没有，才确认这是全新实现。

## 1 顺序是固定的

1. 项目已引入的组件库 / 框架能力里有对应实现，就用它。
2. 项目自己的共享层（组件、工具、布局；叫什么放哪以那个项目的既有约定为准）已有同类实现，就用它。
3. 两边都没有，才手写。**手写的那个要落进共享层**，不许在业务文件里就地长出来。

## 2 不引入第二种约定

项目里已经有一种日期格式化方式，即使你觉得另一种更好，也用现有的。

「写得漂亮」不是换掉现有约定的理由。多一种写法之后，下一个改动的人要先判断「该跟哪一种」，这个判断成本会一直存在；而收益只是一次性的。要换就单独做一次替换，把所有调用方一起换完，不要新增代码时顺手引入第三、第四种。

## 3 复用不等于放弃控制

用组件不等于接受它的默认长相。定制只走它给出的入口：主题变量、design token、插槽与部件、框架允许的局部覆盖。**不改内部结构选择器**——改了就等它升版碎掉。

反面教材（来自真实项目）：把导航手写成 `div` 加自己算 active 类，等于把现成的菜单组件重做了一遍。凡是「自己算高亮、自己拼状态」的地方，先回去看有没有对应的受控属性。

**唯一必须自己算的情况**：组件按精确键匹配高亮（拿 `index` 去比对），此时业务状态要映射成组件要的那个键。

## 4 自检

1. 新增的这类东西，项目里真的没有吗？搜过哪些位置？
2. 我引入的写法，和项目已有的那一种是同一种吗？
3. 手写的东西落在共享层，还是埋在业务文件里？
4. 定制是走组件给的入口，还是改它的内部结构？
5. 有没有「自己算状态」、但其实组件支持受控属性的地方？
