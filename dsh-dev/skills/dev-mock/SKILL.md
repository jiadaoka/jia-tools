# Mock 不是临时脚本

「先随手写个假数据」几乎必然演变成三件麻烦：mock 逻辑散在组件里，改一次要重启一次，最后还漏进生产包。

所以 mock 从第一行就按下面六条搭。**六条都是契约，不是建议**——少一条，两周后就要重构一次。

## 1 六条契约

| # | 契约 | 不满足的后果 |
|---|---|---|
| 1 | 外部化成独立目录，不内联进构建配置的钩子闭包 | 改 mock 要重启打包器 |
| 2 | 改 mock 文件不重启（文件监听 + 模块缓存失效） | 每调一次数据重启一次 |
| 3 | 开关走热重载文件或运行时全局，不只靠启动期环境变量 | 切开关要重启 |
| 4 | 生产零影响：mock 目录物理隔离，只在 dev 配置里引用 | mock 数据泄到生产包 |
| 5 | 支持命名预设（按请求头/参数返回不同数据） | 无法遍历异常、空、超限场景 |
| 6 | 访问模式匹配真实请求形态（见下节） | 拦不到请求，临时重构 |

## 2 挂载点选错是最常见的坑

先确认请求实际发出去长什么样，再决定 mock 挂在哪一侧：

| 请求形态 | 挂载点 | 开关在哪 |
|---|---|---|
| 相对路径（`/api/xxx`） | dev-server 中间件 | Node 侧，浏览器里没有全局开关 |
| 绝对地址（`https://host/api/xxx`）或已部署环境 | 客户端请求拦截器 | 可以暴露运行时全局切预设 |

选错的表现很典型：**本地看着生效，一部署就全 404**；或者反过来，以为浏览器里有 `window.__MOCK__`，验收时找不到它——这种范式里根本不存在那个开关，要去看开关文件或响应内容。

## 3 mock 数据是测试数据

mock 返回的文案、枚举、脏数据都是为了让界面显示成某个样子，**不是产品文案**。不要为了让校验脚本通过去加工它们，也不要为了「看起来一致」把它们搬进正式数据源。

同理，mock 里的异常值（超长字符串、空数组、`null` 字段、超大分页）是**故意**的，不要因为「界面上不好看」删掉——它们正是为了提前暴露界面处理不了的边界。

## 4 什么时候不该建 mock

- 只为了看一眼布局：直接在页面里写死一份数据，看完删掉，不要建 mock 目录。
- 接口已经能用：用真接口，mock 只会带来第二份数据源。
- 只有一条成功路径要看：手写常量比建六条契约便宜。

建了就要按契约维护，否则它会在半年后变成「谁也不敢删、谁也不知道准不准」的第四份数据源。

## 5 自检

1. mock 逻辑在独立目录，还是散在组件/构建配置里？
2. 改一条 mock 数据要重启吗？
3. 切开关要重启吗？
4. mock 目录会不会被打进生产产物？
5. 能不能切到「异常 / 空 / 超限」这几个预设？
6. 挂载点和真实请求的形态匹配吗？部署后还拦得到吗？
