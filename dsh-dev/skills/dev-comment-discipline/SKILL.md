# 注释纪律

## 1 判断标准只有一句

> **注释里说的东西，在当前代码中是否还存在？**

不存在就删。这条能解决绝大多数注释问题，不需要更多规则。

## 2 不写「不存在的历史」

需求中途加过又删掉的字段、换掉的方案、去掉的临时兼容、绕开又恢复的开关——合并之后它们从来就不存在，注释却为它们留了说明。读者只会以为哪里漏了，然后去找一个不存在的东西。

变更原因属于**提交说明、变更请求描述、工单**，不属于代码。代码注释解释「现在为什么是这样」，不解释「为什么曾经不是那样」。

## 3 不写没有信息的注释

| 反模式 | 问题 |
|---|---|
| `// 设置 name` 之于 `setName()` | 复述代码 |
| `@param id id` | 复述签名，且没有回答任何问题 |
| 注释掉的旧实现 | 版本控制已经记住了，不需要第二份 |
| `// 这里可能有并发问题` | 没有结论，读者不知道该不该改 |
| 大段分隔线 | 视觉噪声，不承载信息 |

注释只承载代码表达不了的部分：

- 为什么取这个值（而不是相邻那个看起来更自然的）
- 为什么这里要特殊处理（触发条件是什么）
- 这个顺序为什么不能换（依赖了什么隐式前提）
- 这条限制来自哪条外部约束（协议、法规、上游缺陷）

## 4 公共层的注释不绑业务

公共方法、公共组件、工具类的注释，只回答四个问题：

1. 是什么（语义）
2. 取值范围（合法输入是什么）
3. 能不能为空
4. 有什么副作用（抛错、写库、发请求、改全局状态）

不写「某业务传入」「某页面需要」。写了，后来者会以为改那个业务就得动公共层，也不敢复用——这是公共代码腐化的起点。

私有方法与单业务内部实现可以点业务语义；但一旦提升到公共层，业务名字必须当场去掉。

## 5 注释与代码不一致

只改一侧，不留新旧两版并存。看到「注释说 A，代码做 B」，不要猜哪个对，先确认再改一侧——猜错方向比不改更糟。

## 6 `TODO:` 的语义

它的意思是「这里有意留白，原因与后续动作已登记」。它**不是**「以后再说」的垃圾桶。

- 不借它加兜底分支（比如权限没批下来就先放开）。
- 不借它加额外调用，不借它跳过校验。
- 真正的中间态必须写清四件事：现在是什么、终态是什么、谁来收尾、什么时候必须收尾。

写不出这四行的 `TODO:`，要么现在解决，要么别留。

## 7 什么时候必须写

- 非直觉的实现（为什么不用更直接的写法）
- 外部约束（协议要求、上游缺陷、性能限制）
- 有意的留白（按第 6 节的四行写）
- 破坏性取舍（这里牺牲了什么，为什么可以接受）

## 8 自检

1. 这条注释描述的东西，代码里还在吗？
2. 删掉这条注释，读者会少知道什么？答案若是「没什么」，就删。
3. 公共方法的注释，是否出现了具体业务名？
4. 注释与代码一致吗？不一致时我改的是对的那一侧吗？
5. 有没有把变更原因写进代码，而不是提交说明？
6. 留下的 `TODO:` 写全四行了吗？
