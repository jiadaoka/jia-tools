# 验证由你发起

**写代码的动作在「代码落盘」这一秒结束。** 报告不是终点前的最后一步验证，报告就是交接：我交出改了什么、哪里可能有问题、要跑什么命令；跑不跑、什么时候跑，是用户的动作。

## 0 三条禁止

没有例外，也没有「就试一下」：

- **不构建、不打包**。`npm run build`、`vite build`、`tsc`、`cargo build`、`go build`、`mvn package`、`make`——一条都不跑。
- **不跑测试**。单测、集成、e2e、快照更新、覆盖率，全部等你发起。`node --test`、`pytest`、`jest` 一样算。
- **不起服务**。dev server、preview、`docker compose up`。

这三类只有一个人能发起：你。我交出的是一份可粘贴的命令清单。

## 1 判据：有没有副作用

分界线只有一条：**这条命令会不会产生副作用。**

读文件、`git diff`、`git status`、`grep`、`ls`、看 `package.json` 里有没有那个脚本、把改动的接口签名和调用方一行行对上去——纸面检查免费，随便做。而且必须做：不查就交出去的代码是瞎猜。

**「轻量」不是豁免理由。** `tsc --noEmit` 看着人畜无害，一样要通读整个项目、一样可能写缓存、一样要等半分钟。判断依据是副作用，不是耗时。

## 2 交付形状

写完代码就停手，然后给三样东西：

1. **改了什么**——文件、行为变化、我在纸上核过的边界。
2. **哪里还没被证明**——诚实标出「这段逻辑我没跑过，只做了静态核对」。这比一句「已完成」有用得多。
3. **待跑的命令清单**——按顺序、每条注明它会产出或改动什么、为什么建议先跑它。

命令清单要能直接粘。别写「请自行验证」，那等于把活推回去又不给线索；也别偷偷替用户跑一条「就试一下」。

## 3 授权只覆盖当次

这是最容易破功的地方，写死：

- 用户说「跑一下」，授权的是**那一刻的树**。我之后再改任何一个字符，上一句授权就作废，要重新等开口。
- 用户问「这样能跑吗」「对不对」「有没有问题」，是在**问**，不是在授权。回答「读下来应该没问题，因为 A 调 B 时 B 的入参已经补齐」，然后停。
- 后台任务不算绕过。`run_in_background` 起的 build 仍然是 build，仍然占用户的 CPU 和磁盘。
- 「反正已经装过依赖了」也不是授权。装依赖、连环境本身就是副作用。

## 4 冲突时怎么办

仓库里可能有写死的流程，比如某份 README 写着「改完跑一遍自检再重启 profile」。按本规范，那是**用户的动作**：我把 `node scripts/check.mjs` 递到手上，并说明它验的是什么（挂载路径、description 长度、引用文件是否存在），而不是先跑一遍再告诉他通过了。

需要连续几轮验证才能定位的问题（构建报错要复现才能修），也一样：先交出我读出来的判断和最小复现命令，用户跑、把输出贴回来，我再改。跑的人手里有真实输出，我手里只有推断，两者不该混成一句「应该好了」。

**唯一例外**：用户在同一轮里明确说「改完跑一下」，那是一次当次授权，覆盖到他下一次要求改动为止。

## 5 反面教材

- 改完三个文件，顺手 `npm run build` 确认没编译错，然后把成功日志贴进结论。看起来负责，实际是拿用户的机器给自己发合格证；真报错时，用户看到的第一条信息已经是被加工过的。
- 起 dev server 截图「验证一下界面」。端口被用户自己的实例占着，我的进程静默退到 3001，截图里是旧代码，我还照着它说「已生效」。
- 测试挂了一下，于是加 `-u` 让它过。快照被改写成当前（错误的）行为，之后所有人以为这是基线。
- 用户问「这个改动靠谱吗」，我理解成「去验证一下」，跑了全量测试，四分钟，然后回答了一个用户三秒就能从我给的推理里判断的问题。

## 6 不在管的事

CI 流水线、部署脚本、用户自己敲的命令，都不受这条约束——它管的是我在会话里主动发起的动作。真到需要我盯一次构建结果的时候，等用户说。
