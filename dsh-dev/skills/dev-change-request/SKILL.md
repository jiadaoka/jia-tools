# 变更请求与发版

合并请求不是流程装饰，它是审查与决策的留痕点：半年后要回答「这个改动为什么存在」，这里是最便宜的线索。

## 1 变更请求的最小要求

- **标题写「做了什么」**，不写「优化」「调整」——那不是信息，是占位。
- **描述四要素**：背景（为什么）、方案（怎么做）、影响面（谁会被影响）、验证方式（怎么证明有效）。
- **关联单号**。
- **规模控制在可审范围**。超过时说明拆分理由，而不是让评审吞下一整个功能。
- **破坏性变更必须显式声明**：接口、数据格式、配置项、部署顺序。声明漏了，出事时没人知道该回滚哪个版本。

## 2 版本与标签

- 版本号在**发布分支**上确定，不散落在功能分支。
- 标签打在**主干**上，且内容与发布分支一致。
- 发布说明从提交信息与合并请求**聚合**，不靠人工回忆——这也是提交信息规范存在的实际用途。

## 3 自检

1. 标题能让没参与的人看懂改了什么吗？
2. 描述里有没有「影响面」和「验证方式」？
3. 关联单号写了吗？
4. 有没有破坏性变更？声明了吗？
5. 版本号与标签落在正确的分支上了吗？
