# 依据只读

依据一旦被改，**对照基准就没了**。评审时看到「原型和代码一致」，已经分不清是代码照着原型写，还是原型被改成了代码的样子——这个损失不可逆，因为它没有 diff 可查。

## 1 什么算依据

需求文档、原型（HTML / Figma / 截图）、接口文档、设计稿、验收单。

共同点不在格式，在位置：**它们在开发仓库之外**。改了没有 diff、没有评审入口、没有提交记录，代价由后面所有人承担。

## 2 三件事都不做

| 不做 | 常见的说法 | 实际发生的事 |
|---|---|---|
| 不改 | 「原型这里跟后端返回对不上，我先把它改一致」 | 依据被就地修正，差异从此无人知晓 |
| 不补 | 「原型没画空态和分页，我补一个完善版再照着做」 | 补出来的那版没有评审，却被当成甲方要的样子 |
| 不回写 | 「做完把最终字段和交互整理回需求文档」 | 文档变成实现的说明书，下次没人敢照着它开工 |

第三条最容易被当成好意——「让文档和代码一致」听起来是维护。但文档的价值在**先于实现的约定**，回写之后它就只剩描述，不再约束任何东西。

## 3 差异是事实，不是待修的错

对不上时按三步走：

1. **记录**：哪个功能点、依据怎么写的、实现打算怎么做（或已经这么做）。
2. **分流**：
   - 依据之间互相矛盾（原型与需求文字打架）→ 停下来问，不自己挑一个；
   - 依据缺失、但按最小假设能做完 → 做完，在汇报里点名那是假设；
   - 依据明确、只是实现更费事 → 照依据做，不降级成好写的那版。
3. **汇报时单列一段「与依据的差异」**，一条一行，标明是「按依据做」「按判断做（附理由）」还是「待确认」。

这一段的用处不是免责，是让人在一处看到全部偏离，而不是自己从 diff 里倒推。

## 4 唯一的例外

用户明确要求改需求文档、原型或设计稿。那时按那次任务的要求做，**但不夹在开发里顺手改**——两件事混在一轮里，改动范围就说不清了。

## 5 自检

1. 这一轮我动过需求文档、原型或设计稿吗？哪一句授权允许动它？
2. 实现和依据的出入，写进汇报了，还是被我在依据里「抹平」了？
3. 依据互相矛盾时，我是停下来问，还是自己挑了一个？
4. 「让文档看起来和实现一致」这类动作，是不是正被我当成好意在做？
